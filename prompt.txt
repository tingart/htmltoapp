You are working inside a completely EMPTY GitHub repository.

Build this repository from scratch into a reusable multi-platform build system for my Web OS.

IMPORTANT:
- The repository is currently empty.
- Create everything required from scratch.
- Do not assume an existing Tauri project.
- Use Tauri v2.
- My Web OS is a large HTML/CSS/JavaScript application.

- The goal is NOT simply to wrap a website in an APK.

==================================================

Create this architecture:

Tauri v2 bridge

Sandboxed runtime

The frontend must NOT directly depend on Android, Windows, Linux, or macOS APIs.

Instead expose a common API such as:

window.webOS.terminal
window.webOS.process
window.webOS.network
window.webOS.storage
window.webOS.device
window.webOS.permissions

The exact API design can be improved if necessary.

10. Upload the resulting artifacts.

The permanent repository should remain a reusable factory.

6. SANDBOXED WEB OS RUNTIME
==================================================

This is NOT just a website wrapper.

Design a native runtime layer for the Web OS.

The runtime should conceptually provide:

Filesystem:
    webOS.fs

Terminal:
    webOS.terminal

Process management:
    webOS.process

Network:
    webOS.network

Storage:
    webOS.storage

Permissions:
    webOS.permissions

Device/native functionality:
    webOS.device

The Web OS frontend should communicate with these through a controlled Tauri bridge.

Do NOT expose unrestricted native commands directly to arbitrary frontend JavaScript.

==================================================
7. FILESYSTEM
==================================================

Create a sandboxed virtual filesystem.

The Web OS should have its own filesystem namespace.

For example:

/home/
/home/user/
/home/user/Documents/
/home/user/Downloads/
/tmp/
/apps/

The Web OS must NOT automatically receive unrestricted access to the host operating system filesystem.

Create an abstraction such as:

webOS.fs.readFile()
webOS.fs.writeFile()
webOS.fs.readdir()
webOS.fs.mkdir()
webOS.fs.remove()

Use Tauri's filesystem capabilities where appropriate, but enforce the application's sandbox boundary.

==================================================
8. TERMINAL
==================================================

Design a terminal API:

webOS.terminal.exec(command)
webOS.terminal.spawn(command, args)
webOS.terminal.write(...)
webOS.terminal.resize(...)
webOS.terminal.kill(...)

The terminal must run inside the application's controlled sandbox.

Do NOT expose an unrestricted host shell by default.

The implementation should be platform-aware.

IMPORTANT:

Android is NOT equivalent to desktop Linux.

Do not assume that Android APKs can simply execute arbitrary Linux commands.

For Android, design the runtime so that a Linux-like terminal can be implemented using an isolated userspace/runtime if required.

For desktop platforms, use the safest practical sandbox/process mechanism.

If a full Linux userspace is too large to implement in this initial repository, create a clean runtime abstraction and a working minimal sandbox implementation that can later be extended.

==================================================
9. PROCESS API
==================================================

Provide an abstraction similar to:

webOS.process.spawn()
webOS.process.list()
webOS.process.kill()

Processes must respect sandbox/security boundaries.

Do not allow arbitrary host-level privileges.

==================================================
10. NETWORK API
==================================================

Provide a common API for network operations.

The Web OS should be able to call normal HTTPS APIs.

For example:

webOS.network.fetch(url, options)

or allow normal browser fetch where safe.

Do NOT create separate application-level APIs for every platform.

The frontend API should remain common.

Platform-specific implementation belongs underneath the abstraction.

15. SECURITY
==================================================

Security is extremely important.

Assume the Web OS can execute JavaScript downloaded from its own project.

Therefore:

- never expose arbitrary Rust command execution
- validate all command arguments
- enforce filesystem boundaries
- prevent path traversal
- restrict process execution
- enforce permissions
- do not expose secrets to the WebView
- do not expose GitHub credentials to the WebView
- do not store signing keys in the repository
- use GitHub Secrets for sensitive credentials

Implement safe defaults.
